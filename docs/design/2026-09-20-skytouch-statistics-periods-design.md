# SkyTouch statistics: DAY and MTD periods never promote (design)

**Date:** 2026-09-20. **Scope:** one defect, one file, one test module.
Standalone PR; nothing from OH-22 rides with it.

## The defect

`adaptors/skytouch_hotel_statistics.py` labels its five value columns
`ACTUAL / PTD / LY_PTD / YTD / LY_YTD` (`_PERIODS`, line 30) and sets
`is_prior_year` on the two `LY_*` columns. `stats_promote._CANONICAL_PERIODS`
knows only `DAY / Today / MONTH / MTD / YEAR / YTD`. So at promotion every
SkyTouch stage row except the plain `YTD` column is counted as `ignored`, and
no `usali_statistic_fact` row with `period = 'DAY'` or `'MTD'` exists for a
SkyTouch property.

Measured on `tests/fixtures/skytouch_hotel_statistics_words.json` on main.
That fixture is generated by `scripts/gen_skytouch_mock_fixtures.py`: invented
figures in the real header shape (only the header was recalibrated against the
real pack, commit `ef8b9bc`).

| | rows | promoted | ignored |
|---|---|---|---|
| staged by the adapter | 25 (5 metrics x 5 periods, all five metrics curated in `mapping/statistics.yaml`) | | |
| `promote_statistics(source="SKYTOUCH")` today | | 5 (the `YTD` column) | 20 |

Who reads `period == "DAY"`: `performance.py` (occupancy, ADR, RevPAR, `rooms_sold`
from `ROOMS_OCCUPIED`), `night_audit.py`, `schedule_api.py`, `reporting.py`. Every
one of them sees an empty set for a SkyTouch property. The recalibration
that registered the adapter (PR #79, 2026-08-23) verified parsing against the
real pack but never pinned a promoted fact, which is why this survived: the
promote pins in `test_stats_promote.py` are Opera only, and the one AutoClerk
promote assertion is a `promoted > 0` smoke in `test_k6b_synthetic_year.py`.
It was invisible in the ingest report too: the three `promote_statistics`
call sites in `ingestion.py` pass a literal `0` for `unmapped` and discard
`r.ignored`.

## Decision

**D1. Fix the map, not the adapter.** Add four rows to
`stats_promote._CANONICAL_PERIODS`:

| raw label (adapter) | canonical period | `is_prior_year` |
|---|---|---|
| `ACTUAL` | `DAY` | as staged (False) |
| `PTD` | `MTD` | as staged (False) |
| `LY_PTD` | `MTD` | as staged (True) |
| `LY_YTD` | `YTD` | as staged (True) |

`is_prior_year` is copied from the stage row, which the adapter already sets,
so `LY_PTD` becomes `(MTD, prior)` exactly the way Opera's `YEAR` with
`prior=True` becomes `(YTD, prior)` in `test_promotes_curated_metrics_and_canonical_periods`.

That `PTD` is month-to-date rests on the real export, not on the fixture or
the name: the recalibration commit `ef8b9bc` records the real pack's Total
Rooms row as `120 / 2,520 / 2,512 / 20,640 / 20,481` for business date
6/21. 2520 / 120 = 21 days (June 1 to 21) and 20640 / 120 = 172 days
(January 1 to June 21).

The map is keyed by label alone while `metric_map` is keyed by
`(source, label)`, so the four new labels apply to every source. Checked
against every staging adapter: Opera stages `DAY/MONTH/YEAR`, AutoClerk
`Today/Yesterday/Tomorrow/MTD/YTD`, SkyTouch the five above. The only shared
label is `YTD`, with the same meaning everywhere.

Rejected: making the adapter emit canonical labels (the shape HotelKey uses on
the OH-22 branch). The stage table is the as-parsed record and already holds
`PTD`-labelled rows for every SkyTouch file ingested so far; those rows are
`ignored`, not `skipped`, so a promote re-run picks them up under D1 with no
data migration. Changing the adapter would strand them and would also churn
the fixture-pinned adapter tests for no gain. Canonicalization already lives
in the promote map for Opera and AutoClerk; SkyTouch joins them.

**D2. Pin the cross-module invariant by name.** The map and the adapter are
in different modules and can drift again. A test that iterates
`skytouch_hotel_statistics._PERIODS` and asserts every label is a key of
`_CANONICAL_PERIODS` fails the moment either side changes alone. The
comment in `stats_promote.py` names that test rather than claiming the
sets agree (per the comment-claims rule in
`docs/design/2026-08-31-comment-claims-invariant-design.md`).

**D3. No backfill in this PR.** Unmatched rows are counted `ignored` and
write no fact, and `already` is built only from written facts, so a later
`promote_statistics(source="SKYTOUCH", business_date=d)` for the same date
promotes them. Any database that ingested a SkyTouch pack through
`process_pack` before this ships keeps zero DAY/MTD SkyTouch facts until
promotion is re-run for those dates. There is no production SkyTouch tenant,
and no demo seed path stages SkyTouch statistics today (the synthetic year
has only Opera and AutoClerk properties; see the seed defect noted below), so
the re-run is nobody's task yet. If it becomes one it is a per-date call, not
a migration.

Found while checking that claim, and NOT fixed here: `scripts/demo_seed.py`
feeds its sample documents through `process_file`, whose header-window
detection classifies `docs/reference/samples/SkyTouch - Standard Audit Pack
(mock).pdf` as AutoClerk `rate_plan` (a `Rate Plan` column heading inside the
first 120 words). With `REDSTONE TEST INN` mapped to `SKYTOUCH` in
`mapping/properties.yaml`, `detect` then raises the source-mismatch error and
the sample quarantines. The pack path (`process_pack`, title-based detection
from PR #80) is not what the seed uses. Separate ticket.

## Out of scope

- `segment_promote._CANONICAL_PERIODS` (`DAY / MONTH / YEAR`): fed by Opera
  market statistics and AutoClerk rate plan; neither is SkyTouch, and
  SkyTouch has no segment report.
- The HotelKey adapter on #136 emits canonical labels and is unaffected.
- `test_k6b_synthetic_year.py` expects `Today` for AutoClerk and `DAY` for
  Opera at the stage level; it does not assert SkyTouch periods and is
  untouched.

## Visible effect

Beyond the four `period == "DAY"` readers, `reporting.py` pivots statistic
facts with no period filter into DAY/MTD/YTD cells plus prior-year columns
when priors exist. A SkyTouch property's SOS statistics block therefore goes
from a YTD-only column to the full six-column block. That is the fix working,
and it is a rendered-output change.
